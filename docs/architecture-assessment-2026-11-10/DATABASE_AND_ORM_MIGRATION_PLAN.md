# DATABASE_AND_ORM_MIGRATION_PLAN.md

Phase 02 — Deliverable 5 of 10. **This is one of the three domains explicitly flagged for extra scrutiny ("database ownership... avoid Prisma and Alembic fighting over schema migrations").** VERIFIED facts below are re-confirmed this phase (schema structure from Phase 01's full read, re-validated unchanged since HEAD has not moved; transaction/lock inventory freshly re-derived this phase by direct code reading).

## 1. Schema ownership during the migration — the central rule

**Prisma remains the sole schema-migration authority for the entire duration of the application-logic migration (Deliverable 9).** Alembic is introduced from day one of FastAPI development, but is configured in a **"no-op / reflect-only" mode initially**: its `alembic/versions/` starts with a single baseline migration generated by **introspecting the existing, Prisma-managed database** (`alembic revision --autogenerate` against a already-migrated DB, then hand-verified against `prisma/schema.prisma` field-for-field — never a fresh `CREATE TABLE` set), and Alembic is **never run with `alembic upgrade`/`downgrade` against the shared database** during coexistence. Any new column, table, or constraint needed during the migration is added via a normal Prisma migration (`prisma migrate dev`/`deploy`, exactly as today), and the FastAPI side's SQLAlchemy models + Alembic baseline are updated to match **after** the Prisma migration lands, as a documentation/model-sync step, not a competing migration.

This is not a permanent arrangement — it is the rule for **this migration phase specifically**. A later, separate, explicitly-decided cutover (out of scope for this document, flagged in Deliverable 10) would formally transfer migration authority to Alembic once the Next.js backend is fully retired. Until that explicit cutover: **if anyone ever runs `alembic upgrade` against the shared database before that point, that is a process failure, not a supported path** — this should be enforced practically by keeping Alembic's `sqlalchemy.url` pointed at a read-only or migration-restricted database role in non-local environments, not merely by written policy.

## 2. Full model inventory (VERIFIED, unchanged from Phase 01's direct read — 20 models, 8 enums, re-confirmed present at the same HEAD)

See Phase 01's `CURRENT_ARCHITECTURE_AUDIT.md` §3 for the complete field-by-field inventory (not re-transcribed here to avoid duplication); the summary relevant to the SQLAlchemy mapping:

- **Money columns**: every one is `Decimal(14,2)` in Prisma → map to SQLAlchemy `Numeric(14,2)` (not `Float`, not Python `float`) throughout, with the **same discipline Phase 01 found Prisma enforces (never coerce to native number before persisting)** — see §4 below for the two *display-only* exceptions found this phase that need a conscious decision in the port.
- **Rate columns**: `Decimal(7,6)` → SQLAlchemy `Numeric(7,6)`.
- **Enums**: all 8 Postgres enums (`Role`, `KycStatus`, `ProductStatus`, `ShipmentStatus`, `OrderStage`, `ShipmentActor`, `ShipmentIssueType`, `EscrowEntryType`) map directly to SQLAlchemy `Enum` types backed by the **same Postgres enum types already in the database** (`sa.Enum(..., name="ShipmentStatus", create_type=False)` — critically, `create_type=False`, since the type already exists and must not be re-created or altered by SQLAlchemy/Alembic).
- **Relationships**: every FK's `onDelete` policy (Cascade/Restrict/SetNull, Phase 01 §3.2) must be replicated exactly in the SQLAlchemy model (`ondelete="RESTRICT"` etc. on the `ForeignKey`) — these are enforced at the Postgres level already (Prisma generates real FK constraints), so SQLAlchemy models reading the existing schema will **inherit correct behavior automatically as long as the models are mapped with `ondelete=` matching the already-existing constraint**, not re-declared independently in a way that could drift from the live constraint.

## 3. Transaction boundaries to replicate exactly (VERIFIED this phase, full inventory)

Every one of the following is a `db.$transaction(...)` block in the current Next.js code, with an explicit timeout, that must become an equivalent SQLAlchemy `async with session.begin():` block with the **same multi-model write scope** in FastAPI — this is the direct migration-risk checklist for "transactional guarantees," reproduced in full (not summarized) because partial replication here is exactly the kind of silent regression this phase is designed to prevent:

| Existing transaction | Timeout | Models written | FastAPI equivalent must... |
|---|---|---|---|
| `placeOrderTx` (`orders/service.ts:204-376`) | 20s | SellerOffer, Order, Shipment, ShipmentEvent, OrderLine, EscrowEntry(held), CartItem | Lock offers in sorted id order (deadlock prevention — see §4), conditionally decrement stock, create all rows atomically |
| `cancelOrder` (`orders/service.ts:428-485` region) | 20s | Shipment, SellerOffer, EscrowEntry(refund), ShipmentEvent, Order | Lock all shipments for the order first, guard each transition conditionally |
| `acceptShipment` (`sellerService.ts:244-260`) | 15s | Shipment, ShipmentEvent, Order | Conditional `UPDATE ... WHERE id=? AND sellerId=? AND status='new'`, check affected-row count |
| `packShipment` (`sellerService.ts:278-288`) | 15s | Shipment, ShipmentEvent, Order | Same pattern, `status='accepted'` guard |
| `rejectShipment` (`sellerService.ts:307-333`) | 15s | Shipment, SellerOffer, EscrowEntry(refund), ShipmentEvent, Order | Same guarded-update pattern + stock restore + refund entry |
| `dispatchShipment` (`sellerService.ts:361-422`) | 15s | Shipment, ShipmentEvent, Order | Guarded update on `status IN ('accepted','packed')`, plus doc/e-way/weighbridge validation before the write |
| `acceptDriverJob` (`driverService.ts:140-166`) | 15s | ShipmentEvent only | Audit-only, no status change — simplest to port, lowest risk |
| `deliverDriverShipment` (`driverService.ts:192-327`) | 20s | Shipment, ShipmentEvent, ShipmentIssue, Order | Lock the single shipment row (`SELECT...FOR UPDATE`) before any read, to serialize concurrent OTP submissions |
| `reportDriverIssue` (`driverService.ts:342-411`) | 20s | Shipment, ShipmentIssue, ShipmentEvent, Order | Same single-row lock |
| `addCartItem` (`cart/service.ts:268-306`) | 15s | SellerOffer (lock only), Cart, CartItem | Lock offer before re-reading stock/status |
| `updateCartItem` (`cart/service.ts:314-357`?) | 15s | SellerOffer (lock only), CartItem | Same |
| `createAddress`/`updateAddress`/`deleteAddress` (`orders/addresses.ts`) | default (~5s) | Address only | Maintains single-default-address invariant — lowest financial risk, can be an early migration candidate |

**Default isolation level**: none of the above sets an explicit Postgres isolation level (confirmed by grep this phase — zero hits for `isolationLevel`/`Serializable`/`ReadCommitted`); all run at Postgres's default **READ COMMITTED**, with correctness coming entirely from explicit `FOR UPDATE` locks and conditional `updateMany` guards, not from a stronger isolation level. **The FastAPI port must preserve this same reliance on explicit locking, not assume a stronger default isolation level covers for a missing lock** — SQLAlchemy's async session also defaults to READ COMMITTED against Postgres, so this is a like-for-like default, but it means every lock/guard in the table above is load-bearing and must be ported, not optional hardening.

## 4. Row-locking inventory (VERIFIED this phase — all via raw `SELECT ... FOR UPDATE`, not an ORM-level pessimistic-lock helper)

- `cart/service.ts:264-266` `lockOffer()` — single `SellerOffer` row, called before re-checking stock in both cart mutations.
- `orders/service.ts:222-226` — **all distinct offer ids in the cart, locked in sorted order**, explicitly to prevent deadlocks between two concurrent checkouts that share offers. **This exact "sort ids, then lock in that order" pattern must be ported precisely** — locking in an arbitrary (e.g. cart-insertion) order would reintroduce a real deadlock risk under concurrent checkout load that the current code deliberately avoids.
- `orders/service.ts:436` (`cancelOrder`) — all shipments for the order.
- `orders/driverService.ts:195` — the single shipment being delivered.
- `orders/driverService.ts:344` — the single shipment being issue-reported.
- In SQLAlchemy: `select(...).with_for_update()` is the direct equivalent; the sorted-multi-row-lock pattern needs an explicit `ORDER BY id` in the `SELECT ... FOR UPDATE` query (Postgres does not guarantee lock-acquisition order from an unordered multi-row `FOR UPDATE` otherwise).

## 5. A real, pre-existing gap found this phase, not previously flagged (relevant to migration risk, not solely a migration task)

**`src/server/seller/inventory.ts`'s `updateSellerProduct`/`updateSellerStock` perform a plain `findFirst` then `update`, with no transaction and no row lock.** A seller manually editing stock through the Products UI can race with a concurrent `placeOrderTx` stock decrement — the seller's `update` can silently overwrite a stock value that a simultaneous checkout already decremented, a classic lost-update bug. This is **asymmetric** with the carefully-locked checkout path and is a genuine, currently-live correctness gap in the *existing* Next.js code, independent of any migration. **Decision needed (Deliverable 10)**: should the FastAPI port (a) faithfully replicate this gap as-is (lowest migration risk, but perpetuates a real bug), or (b) fix it during the port by adding the same lock/conditional-update discipline already proven correct elsewhere in this exact codebase (low additional effort, since the pattern to copy already exists in `placeOrderTx`)? This document recommends **(b)** — fixing it is a small, well-understood, low-risk addition precisely because the correct pattern is already proven elsewhere in the same codebase, and "preserve existing behavior" should not be read as "preserve existing bugs" where the fix is this cheap and this well-precedented.

## 6. Decimal-precision exceptions found this phase (display-layer only, not ledger-corrupting)

Two locations coerce a `Decimal` to a native number via `Number()` before summing with `+=`, rather than using `.plus()`:
- `orders/service.ts:108-110` (`toOrderDto`'s escrow-summary aggregation: held/refunded/released totals for a single order's display).
- `orders/sellerService.ts:474+` (`sellerPaymentsSummary`'s balance/ledger aggregation).

Both are **read-only aggregations for display**, never written back to the database — so there is no ledger-corruption risk today, but summing many currency amounts via binary floating point can introduce sub-paisa display error that wouldn't appear in a Decimal-exact sum, and it is inconsistent with the rest of the codebase's otherwise-universal Decimal discipline. **Recommendation for the FastAPI port**: sum using Python's `decimal.Decimal` throughout these two aggregations (trivial to do correctly from the start in new code) rather than porting the `Number()`-coercion as-is — this is a strict improvement with no behavior-compatibility downside (the string-formatted output only needs to match to 2 decimal places, which an exact Decimal sum does at least as well as, and more reliably than, the current float-summation).

## 7. Idempotency mechanism (VERIFIED this phase)

`POST /api/orders`'s `idempotency-key` header (validated: 8–128 chars, `^[A-Za-z0-9._:-]+$`) is combined with the authenticated `userId` via `"ord_" + sha256("{userId}:{key}").hex[:24]` to produce the **Order's own primary key** — not a separate idempotency-tracking table. A retry with the same key and user deterministically maps to the same row; a race between two near-simultaneous identical requests is resolved by letting the second one hit a primary-key uniqueness violation (Postgres error code `23505`/Prisma `P2002`) and re-reading the now-committed row instead of erroring. **FastAPI port**: replicate the exact same hash construction (`hashlib.sha256(f"{user_id}:{key}".encode()).hexdigest()[:24]`, prefixed `"ord_"`) so that **an order ID computed by either backend for the same (user, key) pair is identical** — this matters for the coexistence period (Deliverable 8), where a client retry could plausibly hit either backend depending on routing/deploy timing, and both must agree on the same deterministic ID.

## 8. Seed data, and production-data preservation

Phase 01 confirmed the seed script (`prisma/seed.ts`) is idempotent (upserts on stable keys, skips existing order codes) and produces a small, demo-scale dataset. **For this migration specifically**: `prisma/seed.ts` is not touched, not re-run, and not re-implemented in Python during the application-logic migration — it remains a Prisma/TypeScript tool for populating a fresh database, and continues to be run (if at all) before FastAPI ever becomes the authority, under the Prisma-owns-migrations rule in §1. **No production data is touched by anything in this document** — this entire migration plan is additive (new Python code reading/writing the same tables) and no step here requires a data export, transform, or re-import.

## 9. Rollback and recovery

Because Prisma remains the sole migration authority throughout (§1), and FastAPI's database access is purely additive application code (no schema changes originate from the Python side during this phase), **rollback at the database level is never required by this migration** — if a FastAPI-ported workflow misbehaves, the safe rollback is simply to route that workflow's traffic back to the existing Next.js endpoint (Deliverable 8's coexistence/routing design makes this a configuration change, not a data operation) while the Python implementation is fixed. The one place a real schema rollback could matter is §5's optional stock-locking fix, if implemented via a new column/index — any such change should be a normal, reversible Prisma migration, tested against a disposable copy of the schema before being applied anywhere real.
