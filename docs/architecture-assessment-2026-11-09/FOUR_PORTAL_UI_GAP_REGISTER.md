# FOUR_PORTAL_UI_GAP_REGISTER.md

Principal Architect discovery phase — Deliverable 3 of 8. Strictly read-only. Every reference file is a client-only demo prototype (`localStorage`, seeded mock state, "(demo)"-labelled buttons) — gaps are classified by whether the *production* behavior differs from the *intended UX*, not by whether the demo's own mock-data shortcuts were ported literally. Confidence labels: **VERIFIED** / **PARTIALLY VERIFIED** / **UNVERIFIED** per finding.

Per explicit instruction, the **Admin portal is not gap-compared against its reference** in this document (no implementation exists). §4 gives only a reference-structure description and the one cross-cutting gap finding (its total absence) for completeness.

### Customer workflow trace
Registration → Login → Product discovery → Product selection → Cart → Checkout → Order creation → Order tracking is **fully wired and real**, including: bcrypt (cost 12) registration restricted server-side to `role: customer`; catalogue search/filter/sort against Postgres with serviceability/stock/active-offer filtering; server-recomputed cart pricing (bulk tiers, per-seller delivery fee, tax, coupon) under row locks; checkout that **re-validates stock, serviceability, and the ₹50,000 COD cap twice** (once at preview, once inside the placement transaction) and is idempotent via a deterministic key derived from `userId + client-supplied Idempotency-Key`; real order history and per-shipment tracking with a server-decrypted, time-boxed delivery OTP shown only to the owning customer while the shipment is `dispatched`. **There is no payment-gateway step of any kind** — COD is the only path, by design (D3/D4), not by omission. **VERIFIED.**

### Delivery workflow trace
Assignment (at seller dispatch, driver copied implicitly from the selected vehicle) → Acceptance (audit-only, does not gate anything — **DELV-02**) → Pickup/In-transit (static display only, matching the reference) → Delivery attempt + OTP (real, row-locked, bcrypt-verified, 3-try lockout) → Proof of delivery ("photo" is fabricated — **DELV-04**, the top finding of this entire audit) → Completion (`review` status, 24h window) or Exception (automatic proportional dispute, or explicit 3-type issue report, both real `ShipmentIssue` rows). Driver-side authorization is **VERIFIED enforced server-side** by `driverId` scoping at every query (not merely hidden UI), with `deliverDriverShipment` using a second, explicit ownership re-check in addition to the standard `findFirst` pattern. The OTP chain (generate → bcrypt-hash + AES-256-GCM-encrypt → customer-only decrypt → bcrypt-verify) is fully traced and sound, with one self-flagged open item: **no server-side OTP expiry**, tied to the still-open SMS-channel decision (D5) but not itself a formally logged decision (see Deliverable 8).

## 4. Admin portal — reference structure only (no gap comparison, per instruction)

**Reference** (`buildgrid-platform-admin.html`, read in full for structure): 8-section sidebar nav — `Overview, Approvals, Deliveries, Payouts, Sellers, Users, Activity log, Settings` — sharing the exact same design tokens (`#0B1F3A` nav, `#FFC72C` highlight, Bricolage Grotesque + Figtree) as the three built portals, with a mobile bottom-nav breakpoint at 760px. Each section is data-dense: Overview combines a "needs you today" action queue, platform-health-vs-target metrics, a sales/category breakdown, and an emergency "pause all payouts" control; Approvals is a per-category seller-onboarding queue requiring document + delivery-setup verification before a seller can sell; Deliveries splits into live-tracking and a four-type exception board (disputes/no-response/late/failed) each with type-specific resolution actions; Payouts has KPI cards, a batch-approval table with a "second check" threshold for large payouts, and a named "trusted checker" two-person-control pattern; Sellers is a scorecard/tier table driving search ranking; Users is a combined customer+seller directory with suspend; Activity log is an immutable, searchable audit trail explicitly described as "entries cannot be changed or deleted"; Settings holds the marketplace's global business-rule constants (commission %, late-dispatch penalty %, accept/dispatch/review-window hours, max delivery attempts, second-check threshold) plus delivery-proof policy toggles and two-factor sign-in (stated as mandatory and non-disable-able for the admin account).

**Implementation**: none. Zero routes, zero API surface, zero database model corresponding to any of the above (confirmed independently by the Backend and Database research passes — `requireAdmin()` is defined but never called; there is no admin-specific table of any kind, not even an activity log). This is the single largest structural gap in the entire application relative to the four "principal user experiences" named in this engagement's brief, and it also means several of the above reference sections (dispute *resolution*, payout *approval*, the business-rule-constants screen) describe the **only** place several critical business rules were ever meant to be configurable — today those same constants (`COMMISSION_RATE`, `LATE_PENALTY_RATE`, `ACCEPT_WINDOW_HOURS`, etc.) are hardcoded in `lib/seller/rules.ts`, not configurable by anyone at runtime.

## Cross-portal pattern: the two highest-severity findings share one root cause each

- **SELL-02** (sidebar score mismatch) and **SELL-01** (dead attention-list link) share a root cause: the Seller Overview page is the *last* unmigrated screen reading `SellerStoreProvider`/`data/seller.ts` mock state, in a portal where almost everything else has already moved to real data — so the mock/real seam is maximally visible exactly where a seller looks first.
- **DELV-04** (fake photo proof) and **SELL-06** (KYC cheque can never be verified) share a root cause: **there is no file-upload capability anywhere in the backend** (Deliverable 2 §2.3). One missing capability, two separately-discovered "broken feature" symptoms in two different portals.
