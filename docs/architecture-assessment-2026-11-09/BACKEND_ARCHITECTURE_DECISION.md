# BACKEND_ARCHITECTURE_DECISION.md

Principal Architect discovery phase — Deliverable 5 of 8. This document evaluates whether to retain the existing Next.js backend, move to a separately-deployed FastAPI backend, or some hybrid — as instructed, with no assumption that the decision is pre-made.

## 0. A conflict that must be resolved before anything else here is actionable

`DECISIONS.md` row **D2** (approved 2026-11-05, by the project owner) reads, verbatim:

> **Stack: Next.js (App Router, TypeScript) full-stack + PostgreSQL + Prisma, bcrypt + server-session auth, Tailwind, Zod (API validation), Vitest. No microservices.** — **APPROVED**. Rejected alternatives (recorded in the same row): *"Next+SvelteSplit, separate Spring Boot API (slower to deliver, second deploy target), **Python/FastAPI re-frontend cost**, plain HTML+vanilla JS w/ thin API."*

This is not a casual note — it is a formally approved architecture decision, with FastAPI explicitly considered and explicitly rejected, for a stated reason ("re-frontend cost" — i.e., the team's/developer's stronger familiarity with JS/React/Next at the time, per `ARCHITECTURE_PROPOSAL.md §1`). This engagement's own brief states "the company primarily uses Python and FastAPI for backend development" and frames FastAPI as "the leading backend candidate... not yet an approved implementation decision" — a different stated rationale (organizational standard vs. individual developer familiarity) than D2 considered.

**This is a live conflict between two legitimate, differently-motivated inputs, not a case where one side is simply wrong.** D2 was correct given its own premise (a solo/small-team developer optimizing for a 48-hour MVP who knew JS better). The new brief's premise (a company that standardizes on Python/FastAPI, now looking at a longer-term platform, not a 48-hour sprint) is a different and equally legitimate set of constraints. **This document evaluates the question fresh, under the new premise, and explicitly states where its conclusion differs from D2 and why** — per this audit's own instruction not to silently pick a side when sources conflict. **The final choice of premise (continue optimizing for the original team's velocity, vs. re-optimize for organizational Python standardization) is itself Decision-level and is listed in Deliverable 8 as requiring explicit developer/business sign-off — this document's recommendation is conditioned on that choice, not a replacement for it.**

A second, related conflict exists on deployment target (D10 approved Docker; the actual deployed artifact targets Render.com; this brief asks about GCP) — addressed in Deliverable 6 §8, not here.

## 1. What currently exists (recap, full detail in Deliverable 2)

- 39 API routes, 100% traced, consistently ownership-scoped, zero IDOR findings, sound CSRF defense, structured error handling that never leaks internals.
- 20-model Prisma schema with real financial-precision handling (`Decimal(14,2)`/`Decimal(7,6)`, never floats for money) and a mostly-sound (if undocumented-in-full) cascade/restrict policy.
- Real session auth matching current best practice for a server-rendered app (opaque token, hashed at rest, httpOnly cookie) — this is **not** an API-token/JWT model, which matters directly for any split-deployment option (§3).
- A missing, structurally significant piece: **no mechanism of any kind advances a shipment from `review` to `settled`** (Deliverable 4 §2) — this is a defect in the *business logic*, independent of which backend framework hosts it, and would need to be built in Next.js API routes today, or in FastAPI tomorrow, equally either way.
- Zero admin implementation, zero file uploads, zero notification delivery, zero background jobs — all backend-framework-agnostic gaps (Deliverable 2 §2.3).

**The quality of the existing backend logic is high.** This is a material input to the decision: migrating away from it is not "replacing something broken," it is "replacing something that works, to gain other properties" — so the bar for justifying the migration is "what do we gain," not "what do we fix."

## 2. Option evaluation

### Option A — Retain Next.js full-stack
**For**: Zero migration cost or risk. Preserves the verified-sound authorization/validation/transaction patterns exactly as-is. One deployable, one language, one test runner (Vitest already covers the service layer against real Postgres). Session-cookie auth needs no redesign. The team (whoever continues this specific codebase) has already built deep, correct domain knowledge here (Decimal money handling, the escrow state machine, OTP crypto) — that knowledge is Next.js-code-shaped today, and would need to be re-expressed, not just translated, in a second language.
**Against**: Does not align with a company standard of Python/FastAPI, if that standard is organization-wide and durable (not just this one developer's prior preference). Next.js API routes co-locate frontend and backend in one deployable, which cuts against "a well-structured, independently deployable frontend and backend" if that is a hard requirement (it is achievable within Option A too — see §3 — but requires deliberate separation, not something Next.js forces by default).

### Option B — Next.js frontend + FastAPI backend
**For**: Matches the stated company standard. Gives independent deployability and scaling of frontend vs. backend by construction. Pydantic validation and FastAPI's auto-generated OpenAPI contract are genuinely strong for a team that will have multiple consumers of the API over time (this app's frontend today, a future mobile app, per the brief's own question).
**Against**: This is a **full rewrite of the authorization/business-logic layer**, not a framework swap of equivalent effort to, say, swapping Tailwind for CSS Modules. Every one of the 39 ownership-scoped routes, the escrow/order/shipment state machine, the OTP crypto, and the Decimal-exact money math would need to be re-implemented in Python (SQLAlchemy or a Prisma-Python-equivalent, Pydantic schemas mirroring the Zod ones, a new session-auth bridge since FastAPI has no built-in equivalent to Next.js's httpOnly-cookie-session-in-the-same-process pattern — a stateless JWT is the idiomatic FastAPI-world default, which is a deliberate, security-relevant change from the current revocable session model, not a neutral implementation detail). The existing 90+ DB-integration Vitest tests would all need re-writing in a Python test framework to regain equivalent coverage before this could be trusted at parity with today. This is realistically a multi-month, multi-person-week effort for a correctness-sensitive marketplace (money, escrow, multi-seller order splitting) — not a "leading candidate" lightly adopted.

### Option C — Hybrid migration
**For**: Lets the team start writing *new* work (e.g., the admin backend, which doesn't exist yet in either language — §4 below) directly in FastAPI from day one, without touching or re-risking the already-correct, already-tested Next.js order/cart/seller/driver logic. This converts an all-or-nothing migration risk into an incremental one.
**Against**: Running two backend frameworks simultaneously means two auth stories (the existing cookie session vs. whatever FastAPI uses), two deployment artifacts, two sets of environment/secrets, and a real question of how the two services share the one PostgreSQL database safely (two ORMs, two migration systems, unless one is designated as schema-owner and the other reads through a shared, frozen contract). This is more operational complexity than either pure option, and needs an explicit, narrow charter (e.g., "FastAPI owns only net-new admin endpoints, reading the existing schema read-only via SQLAlchemy reflection, writing only to new admin-specific tables") to avoid becoming an unmanaged dual-stack mess.

### Framework comparison, as instructed (FastAPI vs. Django REST Framework vs. NestJS vs. current Next.js API routes)
- **FastAPI**: best fit *if* Python is truly the organizational standard — async-native, Pydantic validation is comparable in spirit to the project's existing Zod discipline, auto-OpenAPI is a genuine win for a future mobile client. Weakest fit for *this specific codebase's* existing auth model (cookie-session vs. FastAPI's typical stateless-token idiom) and for migrating Decimal-exact financial logic (Python's `decimal.Decimal` is a fine equivalent, but every line needs re-writing and re-testing, not transpiling).
- **Django REST Framework**: heavier, more opinionated/batteries-included than this project needs (it already has its own validation/ORM/auth conventions via Prisma+Zod+hand-rolled sessions that don't map cleanly onto Django's); would fight the project's existing patterns more than FastAPI would. Not recommended unless the organization's Python standard is specifically Django, not "Python" generically.
- **NestJS**: would keep the team in TypeScript (so Zod schemas, and even some service-layer logic, could realistically be ported with much less re-writing than a language change requires), and its decorator-based DI/module structure maps well onto the "domain boundaries" this brief asks about in Deliverable 6. It does **not** satisfy "the company primarily uses Python and FastAPI" if that is a hard organizational requirement, but it is the **technically closest option to a true like-for-like migration of the existing business logic with the least rewrite risk**, if the primary goal is "separately deployable frontend/backend" rather than specifically "Python." This is flagged for the business decision, not quietly substituted for the stated preference.
- **Current Next.js API routes**: already does everything the brief's own API-design concerns (Pydantic-style validation, dependency injection, async DB access, versioning, error handling) ask for, via Zod/async Prisma/a shared `handleApi` wrapper — just not with FastAPI's auto-generated OpenAPI contract, which is the one concrete capability gap worth naming honestly (Next.js API routes have no first-class equivalent; it would need to be hand-maintained or generated via a third-party tool like `next-swagger-doc` if an OpenAPI contract becomes a hard requirement, e.g. for a future mobile client).

### FastAPI assessment, if Option B or C is chosen (as instructed, covering the brief's specific sub-questions)
- **Modular structure**: mirror the existing domain split already proven out in `src/server/**` (catalog, cart, orders, seller, driver) as FastAPI routers/packages — this is a direct, low-risk translation of an already-good boundary, not something to redesign from scratch.
- **Dependency injection**: FastAPI's `Depends()` can replace the current `requireSeller()`/`requireDriver()` pattern almost 1:1 conceptually (a dependency that resolves the authenticated principal and 404s/403s otherwise) — this part of the migration is genuinely low-friction.
- **Pydantic validation**: direct conceptual replacement for the existing Zod schemas; the *rules themselves* (GSTIN regex, phone regex, Decimal bounds) can be transcribed, not redesigned.
- **SQLAlchemy vs. existing Prisma**: this is the single biggest-effort item. SQLAlchemy (ideally 2.0-style, async) can express the same 20-model schema, but every relation, cascade policy, and the `Decimal(14,2)`/`Decimal(7,6)` precision discipline must be re-declared and re-verified — **this is where migration risk concentrates**, because money-precision bugs are exactly the class of defect this audit found zero instances of in the current Prisma schema, and a rewrite is the highest-risk moment to introduce one.
- **Alembic**: standard, sound choice to replace Prisma Migrate; the two already-applied Prisma migrations would need to be re-expressed as an initial Alembic baseline against the *same* live database (not a fresh one), which is a one-time, careful, data-preserving task, not a redesign.
- **Auth compatibility**: as flagged above, this is the one place where "compatibility" is not automatic — a straight FastAPI-idiomatic rewrite would default to JWT, which is a **security-relevant regression** from the current revocable-session model (D21 explicitly rejected JWT "no revocation/logout" when choosing the current scheme) unless deliberately avoided by implementing the same opaque-token-plus-server-side-session-table pattern in FastAPI too (fully possible, just not the framework's default path, so it must be a conscious choice, not an accident of following a FastAPI tutorial).
- **Async DB access**: real and straightforward with SQLAlchemy 2.0 async + asyncpg.
- **Background workers**: genuinely useful here — **this is the one place a backend-framework change could directly fix a confirmed real defect** (Deliverable 4 §2's missing `review → settled` transition), since FastAPI's ecosystem (e.g. APScheduler, or a lightweight Celery/RQ setup) makes "a recurring job that checks `reviewEnds < now`" a natural, idiomatic addition — but note this exact same fix is equally buildable as a scheduled Next.js route/cron trigger today, at a fraction of the cost of a full migration, and does not require choosing FastAPI to get it. **Do not let "FastAPI makes background jobs easy" be the deciding argument for a full migration when the missing feature itself can be built in an afternoon in the current stack.**
- **API versioning / OpenAPI**: FastAPI's strongest, most genuine advantage over the status quo — auto-generated, always-in-sync-with-code API docs, valuable the moment there is a second real consumer (a mobile app, per the brief's own question) of the same backend.
- **Error handling**: FastAPI's exception-handler pattern can replicate the current `ApiError`/`errorResponse()` discipline (structured `{error:{code,message,field?}}`, no leaked internals) almost exactly — this is not a capability gap either way.
- **Testing strategy**: `pytest` + `httpx.AsyncClient` + a real or dockerized test Postgres would replace the current Vitest-against-real-Postgres pattern — same philosophy, different tools, no loss of rigor if done carefully, but it is net-new test-writing work for every one of the ~90 currently-passing integration tests, not a transliteration.

**Do not introduce Redis, Celery, Kubernetes, or microservices as part of this decision.** None of today's confirmed gaps (missing settlement job, missing admin surface, missing file uploads) require them — a single scheduled task, a single new router group, and a single file-storage integration (e.g. object storage + a signed-URL upload endpoint) respectively are sufficient, in either Next.js or FastAPI. This is explicitly called out because "we're evaluating FastAPI" conversations often drift into "and therefore also Celery/Redis/K8s," which would be premature complexity for this system's actual current scale (a handful of sellers, tens of orders in the seed data) and against this engagement's own stated preference for a modular monolith.

## 3. Recommendation

**Primary recommendation: Option C (hybrid, narrowly scoped), conditioned on confirming the premise question in Deliverable 8 first.**

Concretely:
1. **Do not rewrite the existing, verified-sound Next.js order/cart/seller/driver backend.** It is correct, tested, and the single highest-quality part of this codebase by a wide margin (Deliverable 2 §2.1). Rewriting it is the highest-risk, lowest-necessity option on the table.
2. **Build net-new backend surfaces (starting with the admin backend, which does not exist in any language today) in FastAPI**, if the organizational Python standard is confirmed as a genuine, durable requirement (not just a preference this one evaluation should defer to without checking). This gets the team real FastAPI experience on the codebase's own domain, on net-new code, with zero regression risk to what already works.
3. **Fix the confirmed `review → settled` settlement gap immediately, in the current Next.js stack**, regardless of the FastAPI decision's timeline — it is a release blocker today and the fix (a scheduled check) is a day of work, not a multi-month migration prerequisite.
4. **If and only if** the organization later decides the *entire* backend must be Python (not just net-new work), treat that as a second, separate, deliberate, multi-month project with its own roadmap — do not fold it into "while we're adding the admin portal."
5. If "Python specifically" turns out to be negotiable and the real goal is "a separately deployable, strongly-typed backend with less rewrite risk," **NestJS is worth an explicit side-by-side conversation** before committing to the larger rewrite, precisely because it could reuse far more of the existing Zod-validated, TypeScript-typed business logic than any Python framework can.

This recommendation differs from D2 only in degree, not in kind: D2 said "no FastAPI, full-stack Next.js, no microservices." This document says "no *wholesale* FastAPI rewrite of what already works, but FastAPI is a reasonable, low-risk choice for the net-new admin surface if Python is a genuine organizational requirement" — a narrower, hybrid conclusion that respects both D2's original reasoning (the existing code is sound, rewriting has real cost) and the new brief's organizational context (Python/FastAPI preference), rather than treating either as automatically overriding the other.
